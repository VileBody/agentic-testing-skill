# Как BDD помогает обнаруживать пропуски

Авторские учебные примеры, 26 октября 2026. Это проект спецификации, а не выполненные автотесты. Условные решения явно указаны; их нельзя автоматически переносить в реальную задачу.

Основа: [BDD](https://cucumber.io/docs/bdd/), [Example Mapping](https://cucumber.io/blog/bdd/example-mapping-introduction/) и [Gherkin](https://cucumber.io/docs/gherkin/reference/). Выбор данных, таблиц и дефектов ниже — наша конструкция.

## 1. Majority vote: сначала правила и неизвестные

Цель: получить консенсус для каждого объекта по действующим оценкам разных асессоров.

| ID | Предлагаемое правило для примера | Что надо уточнить в реальной задаче |
|---|---|---|
| R1 | Объект задаётся `(project, job, question)` | Полный ли это бизнес-ключ? |
| R2 | У каждого асессора один голос: с максимальным timestamp внутри объекта | Что означает время: событие, поступление, исправление? |
| R3 | Допустимые метки — целочисленные 0 и 1 | Нужны ли другие классы, веса и преобразование типов? |
| R4 | Выбираем метку с большим числом действующих голосов | Majority или plurality при нескольких классах? |
| R5 | При равенстве возвращаем 0 | В реальной задаче политика может быть другой |
| R6 | Результат содержит значение для каждой исходной строки, в исходном порядке и с тем же индексом | Нужна ли вместо этого одна строка на объект? |
| R7 | Вход не изменяется | Разрешены ли in-place операции? |

Открытые вопросы: одинаковые timestamp с конфликтующими метками; отсутствующая дата; NULL в ключе; NULL в метке; пустой вход; ошибочный результат пользовательского tie-breaker. Пока ответ не установлен, это вопросы, а не тесты с выдуманным expected.

Для следующих примеров используем R1–R7 и валидные записи с разными timestamp внутри истории одного асессора. Далее отдельно показано, как могла бы выглядеть согласованная политика ошибок.

## 2. Различающий пример дедупликации

Исходные записи относятся к одному объекту. Порядок намеренно не хронологический.

| Позиция | Исходный индекс | Асессор | Время, UTC | Метка |
|---|---:|---|---|---:|
| 0 | 90 | A | 2026-01-04 00:00 | 1 |
| 1 | 10 | C | 2026-01-01 00:00 | 1 |
| 2 | 90 | A | 2026-01-02 00:00 | 0 |
| 3 | 7 | B | 2026-01-01 00:00 | 0 |
| 4 | 42 | A | 2026-01-01 00:00 | 0 |
| 5 | 3 | A | 2026-01-03 00:00 | 0 |

После выбора новых оценок остаются A=1, B=0, C=1. Ожидаем шесть единиц, индекс `[90, 10, 90, 7, 42, 3]`, неизменный вход.

Если посчитать все события, победит 0: четыре нуля против двух единиц. Если выбрать последнюю строку A без сортировки по времени, тоже победит 0. Пример не зависит от tie-breaker, в отличие от исходного четырёхстрочного примера, где неправильная дедупликация давала ничью.

```gherkin
Feature: Consensus from current assessor votes
  Rule: Only the latest vote of each assessor counts within an object

    Scenario: Earlier revisions do not outweigh current votes
      Given one object has the following vote history
        | assessor | timestamp            | label |
        | A        | 2026-01-04T00:00:00Z | 1     |
        | C        | 2026-01-01T00:00:00Z | 1     |
        | A        | 2026-01-02T00:00:00Z | 0     |
        | B        | 2026-01-01T00:00:00Z | 0     |
        | A        | 2026-01-01T00:00:00Z | 0     |
        | A        | 2026-01-03T00:00:00Z | 0     |
      When consensus is calculated
      Then the consensus for each original row is 1
```

Это описание ещё не исполняется: для Gherkin нужны step definitions и runner. На интервью его проще перевести в обычный pytest. Контракт индекса и неизменности входа можно проверить отдельными ясными assertions.

Ещё нужен пример с различающимися результатами групп: у project=P вопрос Q получает 1, у project=R тот же Q получает 0; строки перемешаны. Только такой пример проверит привязку разных результатов к исходным строкам — шесть одинаковых единиц выше не обнаружат перестановку значений внутри ответа.

## 3. Таблица решений закрывает то, чего не гарантирует Gherkin

Предположим, после обсуждения дополнительно выбрали такой контракт: пустой вход возвращает пустой результат; NULL/невалидные значения отклоняются; конфликтующие оценки одного асессора в один момент отклоняются; точный дубль события не меняет результат. Это учебное решение.

| Состояние | Ожидаемое поведение | Различаемый дефект |
|---|---|---|
| Пустой вход | Пустой результат установленного типа | Падение на `max`/первой строке |
| Невалидная запись | Согласованная validation error, вход неизменен | Молчаливый coerce/drop |
| Валидные записи, одинаковые время и метка | Считаются одним действующим голосом | Повтор усиливает вес асессора |
| Валидные записи, одинаковое время, конфликт меток | Согласованная conflict error | Случайный выбор по порядку строк |
| Конфликтов нет, действующие голоса дают `n1 > n0` | 1 | Инверсия результата |
| Конфликтов нет, `n0 > n1` | 0 | Константная реализация, всегда 1 |
| Конфликтов нет, `n0 = n1 > 0` | 0 по R5 | Неверная tie policy |

Таблица задаёт и порядок анализа: сначала пустота/валидация, затем разрешение истории, затем сравнение голосов. Если одновременно встречаются разные ошибки, нужно определить допустимую категорию/набор ошибок либо приоритет; случайный текст исключения не становится контрактом.

Для каждого решения нужны конкретные входы. «Валидный/невалидный» затем раскрывается на значимые классы; это таблица поведения, не доказательство покрытия всех возможных значений.

## 4. Свойства с явными предпосылками

| Свойство | Предпосылки и способ сравнения | Что может поймать |
|---|---|---|
| Перестановка входа сохраняет консенсус объектов | Выбор при равном времени определён; сравниваем по полному ключу, не голые списки строк | Зависимость от случайного порядка |
| Добавление строго более старого голоса существующего асессора ничего не меняет | Та же группа; все записи валидны | Подсчёт старых оценок |
| Добавление голоса нового асессора за строгого победителя сохраняет победителя | Асессор действительно новый; веса равны | Неверное обновление счётчика |
| Биективное переименование асессоров сохраняет результат | Tie policy не зависит от ID | Случайное смешение ID и меток |
| Другой объект не меняет результат данного | Сравниваем только исходный объект; полный ключ | Нарушение изоляции |
| Точный дубль события ничего не меняет | Контракт признаёт такой дубль повтором | Лишний голос |

Свойства дополняют ручные ответы. Например, функция «всегда 0» выдержит многие инварианты, но провалит пример с победой 1.

## 5. Отдельный API-пример: результат и побочный эффект

Учебный контракт: у одного клиента повтор запроса с тем же ключом и тем же payload возвращает тот же order ID; другой payload с этим ключом вызывает конфликт; разные клиенты имеют независимое пространство ключей. Запись заказа и фиксация обработанного ключа должны сохраняться атомарно.

```gherkin
Feature: Safe order retries
  Rule: A retry must not create a second order

    Scenario: The response is lost after the order is committed
      Given client Alice has no order for request key K
      And Alice submits payload P using request key K
      And the order is committed but the response is lost
      When Alice retries payload P using request key K
      Then Alice receives the identifier of the original order
      And exactly one order exists for Alice and request key K
```

Здесь `Then` проверяется через наблюдаемый API заказов либо через явно выбранную интеграционную проверку хранилища — в зависимости от уровня теста. Чтение внутренней таблицы само по себе не становится пользовательским критерием приёмки.

Что этот сценарий обнаруживает: повторное создание после успешной обработки и потери ответа. Чего не обнаруживает: два одновременных первых запроса. Для этого нужен отдельный тест с контролируемым пересечением исполнения и настоящим механизмом уникальности/транзакций.

| Событие / состояние | Ожидание по учебному контракту |
|---|---|
| Первый запрос | Один новый заказ |
| Повтор после commit и потери ответа | Тот же ID, заказ по-прежнему один |
| Тот же ключ, другой payload | Конфликт, старый заказ неизменен |
| Другой клиент, тот же ключ | Независимый заказ |
| Сбой до commit | Нет частичного заказа; retry может создать один |
| Два первых запроса одновременно | Один заказ; результаты соответствуют выбранной политике ожидания/конфликта |
| Повтор после истечения срока хранения ключа | Открытый вопрос, требуется отдельная политика |

Идея теста с потерей ответа основана на инженерном описании [идемпотентных API AWS](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/); конкретный заказный контракт придуман здесь.

## 6. Практический вывод для скилла

Полезная комбинация: **правило → пример → таблица решений/состояний при необходимости → исполняемая проверка → правдоподобный дефект**. Gherkin можно использовать для ясности, не превращая установку Cucumber в обязательный этап. Неизвестный expected остаётся вопросом, а не поручением агенту самостоятельно придумать бизнес-правило.
