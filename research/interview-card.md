# Карточка для интервью

Рабочий черновик. Предлагаемые бюджеты — наша эвристика, ещё не проверенная на серии интервью.

## Перед реализацией

Сформулировать цель и контракт: вход, результат, ключ объекта, порядок/время, ошибки, побочные эффекты. Отделить важные неизвестные от мелких технических решений.

Затем спросить:

1. Какое неверное бизнес-решение здесь наиболее вероятно или дорого?
2. Какой маленький вход отличит правильную реализацию от этой ошибки?
3. Откуда независимо известен ожидаемый ответ?
4. На каком уровне ошибка проявится: функция, адаптер, БД, пользовательский путь?
5. Как убедиться, что проверка действительно выполнилась?

## Минимальная матрица

| Правило / риск | Различающий вход | Expected и его основание | Уровень / тест | Статус |
|---|---|---|---|---|
| Повтор не увеличивает вес участника | Старые голоса меняют победителя при ошибочном подсчёте | Ручной расчёт по правилу latest wins | Unit | Запланирован |
| Объекты независимы | Один question, два project, противоположные ответы | Два отдельных расчёта | Unit | Запланирован |
| Ответы привязаны к исходным строкам | Смешанные группы с разными победителями, сложный индекс | Явная последовательность и индекс | Unit | Запланирован |

Статусы: запланирован, реально прошёл, упал, пропущен, не удалось запустить. Для фактического запуска добавляются команда, проверенное состояние и краткий вывод.

## Маршрут выбора

- Несколько условий меняют решение → небольшая таблица решений.
- Есть retry, кэш, отмена, история → последовательность состояний.
- Простая функция → ручные примеры и границы.
- Сложная оптимизация → простой oracle и генеративное сравнение.
- Нет полного oracle → обоснованные свойства, дополненные хотя бы некоторыми известными ответами.
- Важна реальная внешняя граница → один нужный интеграционный путь.
- Риск подгонки тестов → конкретный mutation probe, если позволяет время.

## Пример распределения 45 минут

| Время | Результат |
|---|---|
| 0–5 | Контракт, важные вопросы, несколько главных рисков |
| 5–12 | Первые различающие примеры и осмысленный RED |
| 12–30 | Небольшие циклы реализации и проверки; следующие тесты по мере необходимости |
| 30–38 | Проверка наиболее опасного оставшегося риска другим способом |
| 38–45 | Нужные финальные проверки, объяснение решения и ограничений |

Не обязательны ни пять тестов, ни property-based framework, ни мутация. Если риск не успели проверить, назвать его. Не тратить последние минуты на новый тестовый фреймворк вместо демонстрации работающего решения.

## Шаблон задания агенту

```text
Сначала сформулируй наблюдаемый контракт и отдели установленные правила
от предположений. Для неоднозначности, меняющей ответ, покажи конкретные
альтернативные исходы; продолжай части, которые от неё не зависят.

Выбери самые важные правдоподобные ошибки этой задачи. Для каждой укажи
маленький различающий вход, ожидаемый результат и независимое основание
этого результата. При сочетании условий используй таблицу решений;
при зависимости от истории — короткую модель состояний.

Для значимой новой логики используй короткие TDD-циклы. Проверь причину RED,
затем реализуй поведение и запусти подходящие проверки. Не ослабляй
ожидания ради зелёного статуса. Ошибку в тесте можно исправить,
объяснив это через контракт.

Добавь property, независимый oracle, интеграцию или mutation probe только
если это проверяет существенный риск, не закрытый более простой проверкой.
Укажи предпосылки свойств. Не копируй алгоритм SUT в expected.

Сохраняй темп интервью. В конце дай реальные команды и результаты,
что осталось непроверенным и почему. Не называй unrun/skip успешной проверкой.
```

Для обычной задачи этот шаблон можно сокращать. Его эффективность ещё предстоит сравнить с коротким базовым промптом.
