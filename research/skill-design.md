# Проект будущего скилла

Статус: исходный дизайн; первая версия `design-tests` реализована в [skills/design-tests](../skills/design-tests/SKILL.md). Начальный парный прогон и его ограничения описаны в [evals](../evals/README.md). Программа более широкой оценки ниже остаётся актуальной.

## Назначение и границы

Помочь агенту выбрать и выполнить содержательные проверки при реализации поведения, исправлении дефекта или подготовке решения на coding interview. Ключевой результат — проверенная связка «правило → правдоподобный дефект → различающий тест → evidence».

Скилл не должен самовольно менять требования, превращать малое исправление в аудит, требовать отдельного агента на каждую задачу или добавлять новые зависимости без необходимости. Применимые команды и ограничения берутся из текущего проекта.

## Предлагаемая структура

```text
design-tests/
  SKILL.md
  references/
    bdd-and-test-design.md
    test-quality.md
    data-ml.md
    stateful-api.md
    ui.md
```

Файлы добавлять по реальной потребности. Основной SKILL.md содержит критерии выбора, essential checks и ссылки на нужные профили. Исследовательский каталог остаётся в репозитории для человека; не надо заставлять модель читать его целиком при каждом вызове. Такой подход согласуется с [OpenAI о скиллах](https://developers.openai.com/blog/rethinking-skills-and-prompts-for-gpt-6-astra).

## Решения, которые скилл должен менять

| Ситуация | Ожидаемое решение агента |
|---|---|
| Неясная бизнес-семантика | Показать различающиеся исходы, не выдумывать expected |
| Есть пороги и комбинации правил | Выбрать границы/таблицу решений |
| Есть история и повторные вызовы | Добавить последовательности и последствия |
| Оптимизация сложнее простого алгоритма | Рассмотреть независимый reference oracle |
| Property слишком слабое | Найти неверную реализацию, которая его удовлетворяет |
| Все данные симметричны | Добавить различающие группы, метки и порядок |
| Тесты зелёные, но неясно что запускалось | Проверить discovery, target и состояние файлов |
| Низкий риск и мало времени | Ограничиться достаточной дешёвой проверкой |
| После изменения требований тест неверен | Обоснованно исправить тест, сохранив трассировку к правилу |

## Как проверим полезность скилла

Нужен небольшой benchmark, не основанный на проверке слов в ответе. Его постановка — авторское предложение; организация trials и graders опирается на [Anthropic об evals](https://www.anthropic.com/research/demystifying-evals-for-ai-agents).

Начальный банк задач:

1. Majority vote: scope ключа, история оценок, порядок и повторяющийся индекс.
2. Агрегация транзакций: границы окна, единицы измерения, округление, пропуски.
3. Idempotent API: потеря ответа, изменённый payload, конкурентные запросы.
4. Data pipeline: утечка preprocessing, temporal/group split, доступность признаков.
5. Парсер/codec: round-trip проходит, совместимость со стандартом нарушена.
6. UI-форма: validation, error/loading, клавиатурное управление.
7. Legacy bugfix: старое поведение известно, часть его ошибочна.
8. Малое редактирование текста: скилл не должен навязать тяжёлый testing workflow.

На одинаковых задачах сравнить: короткий базовый prompt; исходную памятку; новую компактную версию. Для BDD — отдельное сравнение с/без discovery и формализации, а не одновременная смена всех инструкций. Держать модель, effort, инструменты и бюджет сопоставимыми; использовать свежие контексты и несколько повторов.

Что измерять:

- обнаружение заранее подготовленных дефектов по классам;
- прохождение независимых acceptance checks финальным решением;
- ложные отказы на правильных реализациях и допустимых рефакторингах;
- неверные требования, добавленные агентом;
- время, токены, долю задач, завершённых в бюджете;
- фактическую исполнимость evidence и необоснованные заявления о pass;
- лишние вопросы, зависимости, инфраструктуру и расширение scope.

Evaluation-набор держать отдельно от обучающих примеров скилла. Он должен содержать новые комбинации уже заявленных правил, а не скрытые бизнес-требования. Показывать разброс и число запусков; маленькая выборка не доказывает превосходство. Удалять инструкции, которые добавляют затраты без наблюдаемой пользы.

## Упаковка первой версии

Созданы короткий SKILL.md, шесть условно загружаемых references, метаданные Codex и инструкция установки. Структурная валидация и начальные прогоны выполнены; результат сравнения с baseline — равенство на одном задании, не доказательство превосходства. Публичный пакет содержит синтетические примеры и воспроизводимый grader; исследование отделено от runtime-контекста скилла.
