# Источники и проверка утверждений

Проверено 26 октября 2026. Ниже — 28 материалов: документация, описания практик и первичные отчёты авторов экспериментов. Это целевой обзор, не систематический метаанализ исследований эффективности тестирования. Полные статьи не перепубликуются.

Тип источника имеет значение: документация подтверждает возможности инструмента; рекомендация автора описывает практику; отдельный эксперимент не устанавливает универсальную причинную связь.

## С чего читать

Для первой сессии: S05 → S04 → S01 → S12 → S14 → S24. Это последовательно даёт выяснение требований, запись поведения, цикл реализации, опыт генеративного поиска багов, ограничение затрат и критическую проверку методологии.

<a id="s01"></a>
## S01

[Martin Fowler — Test Driven Development](https://martinfowler.com/bliki/TestDrivenDevelopment.html), редакция 11.12.2023. **Объяснение практики.**

Подтверждает цикл Red–Green–Refactor и предварительный список тест-кейсов. Для нас: выбирать следующий значимый пример, пополнять список по мере работы. Не подтверждает, что TDD автоматически создаёт полную спецификацию или оптимален для любого изменения.

<a id="s02"></a>
## S02

[Google Testing Blog — Test Behavior, Not Implementation](https://testing.googleblog.com/2013/08/testing-on-toilet-test-behavior-not.html), 05.08.2013. **Инженерная рекомендация.**

Проверки публичного поведения должны переживать внутренний рефакторинг. В статье допускаются обоснованные проверки реализации; запрет всех mocks или interaction assertions из неё не следует.

<a id="s03"></a>
## S03

[Cucumber — Behaviour-Driven Development](https://cucumber.io/docs/bdd/). **Документация метода.**

BDD описан через discovery, formulation, automation и совместное понимание задачи. Это основание для обсуждения поведения перед кодом, но не экспериментальное свидетельство эффективности BDD при работе с LLM.

<a id="s04"></a>
## S04

[Cucumber — Gherkin Reference](https://cucumber.io/docs/gherkin/reference/). **Справочник нотации.**

Определяет Rule, Scenario, Given/When/Then, Scenario Outline и Examples. Нотация структурирует выбранные сценарии; она не проверяет полноту самих требований. Исполнение требует step definitions.

<a id="s05"></a>
## S05

[Matt Wynne — Introducing Example Mapping](https://cucumber.io/blog/bdd/example-mapping-introduction/), 08.12.2015. **Описание метода его автором.**

Разделяет story, rules, examples и questions. Для нас важнее всего не превращать неизвестный исход в придуманное правило. Формальное написание Gherkin не обязано происходить прямо во время обсуждения примеров.

<a id="s06"></a>
## S06

[ISTQB — CTFL Syllabus v4.0.1](https://istqb.org/?download_id=3345&sdm_process_download=1), 15.09.2024; [страница загрузки](https://istqb.org/sdm_downloads/istqb-certified-tester-foundation-level-syllabus-v4-0/). **Учебная систематизация.**

Разделы 4.2.1–4.2.4: классы, границы, таблицы решений, переходы состояний. Для нас — техники поиска пропусков. Покрытие модели нельзя приравнивать к отсутствию всех дефектов программы.

<a id="s07"></a>
## S07

[NIST — Interactions involved in software failures](https://csrc.nist.gov/Projects/automated-combinatorial-testing-for-software/combinatorial-methods-in-testing/interactions-involved-in-software-failures). **Обзор исследований и метода.**

Объясняет t-way покрытие и ограничения pairwise: некоторые дефекты требуют более двух одновременно действующих факторов. Наблюдения в исследованных системах не дают универсальной гарантии, что определённого t всегда достаточно.

<a id="s08"></a>
## S08

[Hypothesis — Integrations Reference](https://hypothesis.readthedocs.io/en/latest/reference/integrations.html). **Документация инструмента.**

Раздел Ghostwriter иллюстрирует round-trip, idempotence, equivalent и другие свойства. Особенно полезно различение доверенного oracle и сравнения реализаций, ни одна из которых не считается полностью доверенной. Сгенерированный тест — отправная точка, а не готовая гарантия.

<a id="s09"></a>
## S09

[Hypothesis — Stateful tests](https://hypothesis.readthedocs.io/en/latest/stateful.html). **Документация инструмента.**

Генерирует последовательности действий, а не только аргументы отдельной функции. Подходит к API с историей. Документация также предупреждает, что простым задачам полноценная state machine может быть не нужна.

<a id="s10"></a>
## S10

[mutmut — Python mutation tester](https://mutmut.readthedocs.io/en/latest/). **Документация инструмента.**

Позволяет вносить мутации и проверять реакцию тестов, выбирать область мутаций и исследовать выжившие варианты. Для интервью предлагаем небольшие доменные mutation probes; это наша адаптация, не требование mutmut.

<a id="s11"></a>
## S11

[Anthropic — Best practices for Claude Code](https://code.claude.com/docs/en/best-practices). **Текущие рекомендации поставщика.**

Ключевой принцип: дать агенту доступный способ проверки работы — тест, build, diff результата, screenshot. Рассматриваются проверки другим контекстом и adversarial review. Это не универсальное требование запускать несколько агентов на каждую задачу.

<a id="s12"></a>
## S12

[Anthropic — Finding bugs across the Python ecosystem with Claude and property-based testing](https://www.anthropic.com/research/property-based-testing), 14.01.2026. **Первичный исследовательский отчёт.**

Показывает поиск свойств, Hypothesis и разбор найденных контрпримеров. Описаны как полезные находки, так и неверное свойство для dateutil; приведён случай подавления исключений в тесте. Для нас: проверять и свойство, и сам тест. Статья о поиске багов в существующих пакетах, а не сравнении всех стратегий разработки.

<a id="s13"></a>
## S13

[Nicholas Carlini / Anthropic — Building a C compiler with a team of parallel Claudes](https://www.anthropic.com/research/building-c-compiler), 05.02.2026. **Отчёт об инженерном эксперименте.**

Описывает 16 агентов, около 100 тысяч строк и большую роль тестового стенда, диагностических сообщений и GCC как внешнего эталона. Это демонстрация конкретного процесса с заметными ограничениями результата; число агентов не является рецептом для интервью.

<a id="s14"></a>
## S14

[OpenAI — Using GPT-6, Testing and verification](https://developers.openai.com/api/docs/guides/latest-model#gpt-6-astra-testing-and-verification). **Текущая рекомендация поставщика.**

Объём верификации следует калибровать под изменение; проверки должны быть содержательными, повторение после успеха — обоснованным. Это поддерживает ограничение лишней работы, но не отменяет тесты для существенных рисков. URL latest-model меняется со временем; дата чтения важна.

<a id="s15"></a>
## S15

[Eric Provencher / OpenAI — Rethinking skills and prompts for GPT-6 Astra](https://developers.openai.com/blog/rethinking-skills-and-prompts-for-gpt-6-astra), 11.09.2026. **Рекомендация по инструкциям агентам.**

Короткие точные триггеры скиллов, условная загрузка подробностей, пересмотр накопленных инструкций. Автор отдельно указывает на риск избыточного тестирования от старых prompts. Для нас: большая исследовательская база не должна целиком загружаться в каждую задачу.

<a id="s16"></a>
## S16

[OpenAI — Using Goals in Codex](https://developers.openai.com/cookbook/examples/codex/using_goals_in_codex). **Руководство по workflow.**

Предлагает определять результат, наблюдаемый способ его проверки и ограничения. Заимствуем принцип доказуемого завершения; для использования карточки интервью механизм Goals не требуется. Указанная в исходном диалоге дата «май» отдельно не установлена по прочитанному тексту.

<a id="s17"></a>
## S17

[OWASP — Application Security Verification Standard](https://asvs.owasp.org/). **Стандарт требований безопасности.**

Даёт основание для выбора применимых проверок web-приложения. Используем как источник security-профиля, не как автоматический повод разворачивать полный аудит в каждой задаче. Полный ASVS в этом исследовании не разобран построчно.

<a id="s18"></a>
## S18

[Pact — Introduction / What is contract testing?](https://docs.pact.io/). **Документация инструмента и метода.**

Описывает consumer/provider проверки сообщений между приложениями. Это более узкий смысл contract testing, чем проверка shape/index локальной функции. Контракт интеграции не заменяет проверку всей бизнес-логики участников.

<a id="s19"></a>
## S19

[Playwright — Best Practices](https://playwright.dev/docs/best-practices). **Документация инструмента.**

Пользовательское поведение, изоляция проверок, устойчивые способы взаимодействия с UI. Для нас — основа UI-профиля; выбор E2E не означает, что всю логику следует проверять только через браузер.

<a id="s20"></a>
## S20

[AWS Builders’ Library — Making retries safe with idempotent APIs](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/). **Первичное описание инженерной практики.**

Рассматривает повтор запроса, идентификаторы и поздно приходящие операции. Помогает проектировать сценарии потери ответа и восстановления. Конкретная политика срока хранения ключей и конфликта payload должна определяться для нашего API.

<a id="s21"></a>
## S21

[scikit-learn — Common pitfalls and recommended practices](https://scikit-learn.org/stable/common_pitfalls.html). **Документация библиотеки.**

Несогласованный preprocessing, data leakage и управление randomness. Источник для разделения fit и transform по выборкам. Наличие Pipeline не доказывает отсутствия всех видов временной или предметной утечки.

<a id="s22"></a>
## S22

[Breck et al. — The ML Test Score](https://research.google/pubs/the-ml-test-score-a-rubric-for-ml-production-readiness-and-technical-debt-reduction/), IEEE Big Data, 2017. **Исследовательская публикация; прочитаны карточка и abstract.**

Предлагает 28 проверок и потребностей мониторинга для production ML. В этой итерации используется как направление расширения; полный текст и все пункты ещё нужно разобрать перед подробным ML-модулем скилла.

<a id="s23"></a>
## S23

[pytest — Flaky tests](https://docs.pytest.org/en/stable/explanation/flaky.html). **Документация test runner.**

Обсуждает общее состояние, слишком строгие assertions, потоки и способы работы с нестабильностью. Для нас: воспроизводимость является свойством тестовой системы, а не следствием одного фиксированного seed.

<a id="s24"></a>
## S24

[Dan Luu — How well do agents use test and verification techniques?](https://danluu.com/agentic-testing/), сентябрь 2026. **Первичный экспериментальный отчёт автора.**

Важен как проверка предположения «название техники в prompt улучшает код». Результаты ограничены выбранными задачами, моделями и настройками. Не переносим ранжирование техник на все интервью; проверяем собственный скилл экспериментально.

<a id="s25"></a>
## S25

[Anthropic — Demystifying evals for AI agents](https://www.anthropic.com/research/demystifying-evals-for-ai-agents), 09.01.2026. **Описание практики оценки агентов.**

Разделяет задачи, trials и graders; обсуждает проверку конечного состояния, ошибки оценивания и калибровку LLM judges. Для нас — источник идей проверки будущего скилла и отдельного профиля для продуктов с LLM внутри.

<a id="s26"></a>
## S26

[Anthropic — LLMs are making formal software verification feasible at a much larger scale](https://www.anthropic.com/research/formal-verification), 22.10.2026. **Свежий исследовательский отчёт.**

Полезен для дальнейшего направления: доказательства конкретных свойств дополняют тестирование. Ограничения прямо включают модель single-threaded RISC-V, определённые входы и entry points. Из работы не следует доказательство всей функциональной корректности библиотек или обязательность formal methods для интервью.

<a id="s27"></a>
## S27

[OpenAI — Iterating Development Workflows with Codex](https://developers.openai.com/cookbook/examples/codex/iterating-development-workflows-with-codex). **Пример организации workflow.**

Поддерживает наблюдаемые acceptance criteria, проверяемые этапы и evidence. Большая предложенная файловая структура — соглашение конкретного рецепта, не обязательный стандарт Codex. Заимствовать весь административный процесс для 45 минут нецелесообразно.

<a id="s28"></a>
## S28

[Anthropic — Claude Code: Best practices for agentic coding, историческая публикация](https://www.anthropic.com/engineering/claude-code-best-practices), 18.04.2025. **Историческая рекомендация.**

В индексированной версии раздела «Write tests, commit; code, iterate, commit» подтверждается tests-first, запуск падающих тестов, реализация без их изменения и опциональная независимая проверка. Сейчас чистый URL перенаправляет на S11; исторический фрагмент прочитан через поисковую выдачу. Не считаем его отдельной актуальной инструкцией продукта.

## Что уточнилось по исходным наброскам

| Утверждение | Результат проверки |
|---|---|
| Fowler рекомендует список тестов до цикла TDD | Подтверждено S01 |
| Anthropic требует Test author → Implementer → Reviewer как трёх разных агентов | Слишком сильная формулировка: S28 описывает этапы и необязательную независимую проверку |
| Agentic PBT-публикация Anthropic вышла в январе 2026 | Подтверждено для blog post: 14.01.2026; связанная работа существовала уже в 2025 |
| У агента был тест с подавлением исключений | Подтверждено S12 |
| Компиляторный эксперимент: 16 агентов, примерно 100 тыс. строк | Подтверждено S13; это не доказательство полной корректности компилятора |
| OpenAI предупреждает об избыточном тестировании | Подтверждено S14 и S15 |
| OpenAI рекомендует наблюдаемые критерии результата | Подтверждено S16 и S27 |
| Два агента обеспечивают независимый oracle | Не следует из источников: общая неверная спецификация остаётся общей ошибкой |
| BDD-нотация гарантированно исключит классы ошибок | Не установлено. Она помогает сделать условия явными; полнота требует отдельного анализа |
| Хороший workflow обязательно требует хотя бы одного property test | Это предложенная эвристика прошлого диалога, не универсальное правило |

## Что исследовать дальше

- Разобрать полный ML Test Score и первичную литературу о metamorphic testing; здесь их полный обзор не проведён.
- Сравнить короткие prompts с новым скиллом на наших задачах, включая варианты без BDD.
- Исследовать ошибки самого генератора тестов: слабые свойства, пустые домены, неверные expected.
- Отдельно изучить numerical, accessibility, migration и distributed-testing профили, если они понадобятся для целевых интервью.
- Периодически перепроверять живую документацию; версии в URL `latest` и `stable` меняются.
